# 关键亮点与踩坑记录

> 面试 / 简历参考：技术亮点 + 踩过的坑 + 可讲述的叙事。汇总自全项目实践。

## 一、核心技术亮点

### 1. 意图分层的 Agentic RAG（最大亮点）

不是"检索+生成"管道，而是**会判断问题性质**的智能体：

- **7 类意图分类** + 规则快通道（高 precision 正则抓闲聊/能力，省 ~4s LLM）
- **三条信息路径自主协调**：KB 检索（可信引用）/ 外部工具（实时）/ LLM 常识
- **source 来源分级**（6 键 5 色徽章）：用户一眼看出答案来自知识库、常识还是工具——**透明分层**是相对通用 LLM 的差异化

### 2. CRAG 自纠闭环

`retrieve → grade → generate → verify →（不达标）rewrite → retrieve`：

- grade 批量评估（1 次 LLM 判全部证据）
- generate 强制 `[n]` 引用 + small-to-big（child 引用 + parent 上下文）
- verify 双校验（grounded + citations_valid）
- MAX_RETRY=2 自纠，达上限诚实降级标 `fallback_unverified`
- **Faith/Cite 稳定 1.0**

### 3. 工具调用三路协调（grade 兜底核心简化）

grade 无证据改向 tool_agent，**一个改动三重收益**：
- ① 兜底判工具（省一次专门 LLM 调用）
- ② router 误判纠正器
- ③ 常识兜底

分层决策：router 不带工具 schema（开放-封闭，加工具不改 router）。

### 4. 混合检索服务端融合

dense(BGE-M3) + Qdrant 原生 BM25，**服务端 RRF 融合**（零客户端再排），dense 主导。payload 存 content（零 IO 直取）。

### 5. 企业级 KB 生命周期

软删元数据 + 物理清理三存储，跨存储一致性三原则：
- **顺序**：Qdrant 先（隔离检索）→ OSS → MySQL 事务
- **事务**：MySQL `execute_transaction` 原子级联
- **幂等**：Qdrant/OSS 删已删不报错，可重试
- **并发保护**：ACTIVE/DELETING/DELETED 状态机，删除中拒绝上传（409）

> RAG 删除铁律：**Qdrant 必须立即硬删**（软删的 chunks 仍会被检索到 = 错误答案）。

### 6. small-to-big 父子块

检索命中 child（精确引用），回拉 parent（完整上下文）——引用最小化 + 上下文最大化。

### 7. 全过程可观测

SSE 流式逐字 + 思考过程面板（step 节点 + thought 推理 + tool_call）+ 监控看板（KPI + 饼图 + 健康灯）。

### 8. ponytail 工程纪律

标准库/已装依赖优先、最短差异、`ponytail:` 标记简化、DRY（`_stream_answer`/`purge_document` 复用）、YAGNI（不过度设计）。

## 二、踩坑记录（非显而易见）

### 入库流水线 4 大坑

| # | 坑 | 现象 | 根因 | 解法 |
|---|---|---|---|---|
| 1 | **Docling 中文路径** | C 扩展读不到包资源 | Win 中文用户名"魏子轩"在 C 扩展层编码丢失 | 改 **PyMuPDF**，从 bytes 打开绕过文件系统 |
| 2 | **Celery+redis RESP3 死结** | HELLO 3 不响应 | redis-py 8.0 默认 RESP3 + 云代理 Redis 不兼容 | 改 **FastAPI BackgroundTasks**（进程内异步） |
| 3 | **presign 非 ASCII 文件名 403** | 浏览器 PUT 403，对象不入库 | 浏览器对已 encode 的非 ASCII 路径再次编码 → 与签名失配 | OSS key 改 **全 ASCII**（`raw/{vid}/{vid}{ext}`）+ 前端查 `resp.ok` |
| 4 | **presign File body 加 Content-Type 403** | 浏览器 PUT 403 SignatureDoesNotMatch | 浏览器给 File 自动加 CT，presigned 签名不含 CT | 前端 body 用 **`await file.arrayBuffer()`**（ArrayBuffer 不加 CT） |

> 💡 坑 3、4 的共同教训：**presigned 签名字节级敏感**；**浏览器隐式行为（重编码/加 CT）是服务端 httpx 测试的盲区**——"测试绿、浏览器红"的差距根因在客户端。

### 其他坑

| 坑 | 解法 |
|---|---|
| **Qdrant host 须带 http scheme** | 无 scheme 默认 https → SSL WRONG_VERSION_NUMBER；`_normalize_host` 自动补 `http://` |
| **Open-Meteo geocoding 不支持中文** | 英文 200，中文返回空 results（英文索引限制）→ `_CN2EN` 常用城市映射 + description 要求 LLM 传英文 |
| **Qdrant payload document_id 误写 version_id** | 按文档删失效；修——传真 document_id，删时按 version_id 删 + 按 kb_id 兜底 |
| **jieba 分词拉低 BM25** | "共有词噪声"（"法国首都"分词后"首都"误命中"英国首都"）；分词实验证伪，sparse 默认用原文 |
| **get_kb 幂等检查 404** | get_kb 过滤 deleted_at，已删 KB 查不到；改用不过滤的裸查询 |
| **后端改代码不生效** | uvicorn 无 reload；旧进程占 8000 → 新进程 bind 失败。重启前 netstat 抓 PID + taskkill |
| **schema vs 运行时建表偏差** | users 补列、conversation_messages 单表——运行时 ALTER 补，schema.sql 不完整 |
| **documents/chunks 计数未过滤软删** | 监控 metrics 数字略偏大（已知小瑕疵） |

## 三、可讲述的工程思维

### 3.1 "测试绿、线上红"的诊断方法

OSS PUT 403：服务端 httpx 测试通过（不加 CT），浏览器却 403。用**隔离变量法**诊断（httpx 逐步加 Origin/Content-Type），定位到浏览器对 File body 的隐式 CT——**客户端隐式行为是服务端测试盲区**。

### 3.2 软删除 + 过滤查询的典型陷阱

`get_kb` 用于"列表过滤"（隐藏已删），但复用于"幂等检查"会导致已删 KB 返 404。**不同用途不能共用同一个查询**——展示查询 vs 幂等查询要分开。

### 3.3 一个改动三重收益（grade 兜底改向）

不新开"判工具"节点，复用 tool_agent 的 auto 模式——**省一次 LLM 调用 + 兼任误判纠正 + 常识兜底**。体现"少即是多"的架构判断。

### 3.4 RAG 删除的特殊性

普通 CRUD 软删即可；RAG 删除**向量必须硬删**（否则被检索到 = 错误答案）。这是领域特有的正确性要求。

## 四、简历叙事建议

> **一句话定位**：基于意图分层的 Agentic RAG 智能问答系统（全栈）

**可展开的技术点**（按面试官兴趣选讲）：

- **Agent 工程**：LangGraph 1.x Command 声明式路由，7 类意图分层，CRAG 自纠闭环（grade/generate/verify/rewrite），工具调用三路协调（KB/工具/常识）
- **检索工程**：BGE-M3 dense + Qdrant 原生 BM25 服务端 RRF 融合，BGE rerank 精排，small-to-big 父子块（引用精确 + 上下文完整）
- **工程严谨**：跨三存储（MySQL/Qdrant/OSS）一致性删除（事务级联 + 幂等 + 状态机并发保护），SSE 流式 + 思考过程可观测，source 来源分级（透明可信）
- **全栈能力**：FastAPI + React 19，JWT 鉴权，阿里云 OSS 预签名直传，监控看板
- **问题解决**：presigned URL 浏览器兼容（编码/Content-Type 双坑）、Celery RESP3 死结、RAG 删除正确性、工具 API 中文限制等真实工程问题的定位与绕过

**差异化卖点**：
1. 不是"调 API 拼管道"，而是**有意图判断 + 三路协调 + 可信分级**的智能体
2. 不是"能跑的 demo"，而是**有企业级数据生命周期 + 跨存储一致性**的工程实践
3. source 徽章让**答案可信度透明**——这是 RAG 落地信任的关键
