# 工具调用路径

> 意图路由 v2：新增第三条信息路径——外部工具调用。涉及 `src/agents/tools.py`（run_tool_agent）、`graph.py`、`prompts.py`。
> 设计文档：`docs/superpowers/specs/2026-08-03-tool-calling-design.md`

## 一、为什么需要工具调用

**问题**：意图路由 v1（6 类）虽解决了闲聊 / 常识，但**缺少"工具调用"路径**：

- "查天气 / 查股价 / 查汇率"这类需**外部实时信息**的问题无路可走
- 它们不是 KB 检索（私有库没有），也进不了 `open_answer`（`OPEN_ANSWER_PROMPT` 护栏明确"不答实时信息"→ `REFUSED`）
- 最终被判 `out_of_scope` 直接拒

用户问"今天北京天气"，得到 `refused`——**不是答错，是系统没能力答**。

**目标**：建立"能区分 **KB 检索 / 外部工具 / LLM 常识** 三类信息源并正确协调"的能力。

**底层已具备**：`llm.py:chat_message(tools=)` 封装了 OpenAI 原生 function calling，`run_search_agent` 已验证 `tool_calls` 往返可用。

## 二、第 7 类意图 tool_call + tool_agent 路径

新增第 7 类 `tool_call`（需实时 / 外部信息：天气 / 股价 / 汇率 / 新闻 / 赛事），新增 `tool_agent` 节点：

```
route ┬─ ... (其他 6 类不变)
      └─ tool_call(新) → tool_agent ──→ END (tool / fallback_unverified)
```

明显工具问题（天气等）router 直判 `tool_call`，**跳过 KB 检索**（不白检索）。

## 三、核心简化：grade 兜底改向 tool_agent

> 这是本次最关键的设计——一个改动同时解决三个问题。

**改动**：`grade` 检索无证据时，从 `goto="open_answer"` 改为 `goto="tool_agent"`。

```
grade 无证据 → tool_agent（带工具, function-calling auto 模式）
                 │
                 ├─ LLM 判定需工具 → 调工具 → source=tool
                 └─ LLM 判定不需工具 → 常识答 → source=fallback_unverified
```

**为什么是核心简化**：tool_agent 的 **auto 模式**让 LLM 自己决定调不调工具，**一并承担了三个职责**：

| 职责 | 说明 |
|---|---|
| ① 兜底判工具 | KB 无证据时，auto 模式自动判断是否需工具——**省掉一次专门判工具的 LLM 调用** |
| ② router 误判纠正 | router 把工具问题误判成 KB → retrieve 无证据 → grade → tool_agent 兜底调工具 |
| ③ 常识兜底 | auto 模式不调工具时，自然回落常识答（原 open_answer 的职责） |

> 💡 ponytail 体现：不新开"判工具"节点，复用 tool_agent 的 auto 模式，一个改动三重收益。

## 四、分层决策（避免 router 臃肿）

| 层 | 职责 | 带工具 schema? |
|---|---|---|
| **router** | 粗分类：KB / 工具 / 常识 / 闲聊 / 越界 | ❌ 不带（省 token，只判 7 类） |
| **tool_agent** | 细决策：调哪个工具、调几次、何时停 | ✅ 带 `EXTERNAL_TOOLS` 全集 |

**开放-封闭原则**：router 不需要知道具体工具名；新增工具只改 `EXTERNAL_TOOLS` 列表，**不动 router**。

## 五、tool_agent 闭环

**`run_tool_agent`** (`src/agents/tools.py`)

ReAct 循环（仿 `run_search_agent`），但**自己生成最终回答**：

```
[system: TOOL_AGENT_PROMPT] + [user: question]
         │
         ▼
   ┌─→ chat_message(tools=EXTERNAL_TOOLS)   (function-calling auto)
   │      │
   │      ├─ 有 tool_calls ──→ _dispatch_tool 执行(如 get_weather)
   │      │                      │
   │      │                      └─ 结果回喂 messages + 推 thought 事件
   │      │                      └─ 循环（MAX_TOOL_STEPS=3）
   │      │
   │      └─ 无 tool_calls ──→ 退出循环
   │                              │
   └──────────────────────────────┘
                  │
                  ▼
         _stream_answer(messages)   统一流式生成最终回答（始终打字机效果）
                  │
                  ▼
         {generation, source: tool(调过) | fallback_unverified(没调)}
```

**设计要点**：
- 循环只负责"调工具收集数据"，退出后统一流式生成最终回答（始终打字机效果）
- 工具结果（如温度）由 LLM 转自然语言，不需 KB 的 `[n]` 引用格式
- 不走 verify（grounded 校验针对 KB 证据，工具结果是事实数据）
- function-calling 不可用 → 回退常识兜底（仿 run_search_agent）
- `_stream_answer` 延迟 import 避免循环依赖（graph import tools）

## 六、天气工具（Open-Meteo）

### 6.1 工具定义

```python
WEATHER_TOOL = {
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "查询指定城市的实时天气...",
        "parameters": {"properties": {"city": {"description": "城市英文名或拼音"}}},
    },
}
EXTERNAL_TOOLS = [WEATHER_TOOL]   # 加新工具只改这里
```

### 6.2 执行函数 `get_weather`

**Open-Meteo 免费无 key**，两步：
1. **geocoding**：城市名 → 经纬度（`geocoding-api.open-meteo.com/v1/search`）
2. **forecast**：经纬度 → 实时天气（`api.open-meteo.com/v1/forecast`）

返回 `"Beijing：26.0°C，阴"`（WMO weather_code → 中文映射）。

### 6.3 ⚠️ 关键坑：geocoding 不支持中文

**实测发现**（2026-08-03）：
- 英文 `Beijing` → geocoding 返回 200 ✓
- 中文 `北京`（含 percent-encoded）→ 返回**空 results** ✗

**根因**：Open-Meteo geocoding 是英文索引，不支持中文 name。非网络问题。

**对策**（ponytail）：
- `_CN2EN`：常用中文城市→英文映射（20 个：北京/上海/广州...）兜底
- `WEATHER_TOOL` description 要求 LLM 传英文 / 拼音

```python
async def get_weather(city):
    city = _CN2EN.get(city, city)   # 中文常用城市→英文, geocoding 为英文索引
    # ... geocoding + forecast
```

**效果**：gpt-4o-mini 把"北京"转成 `Beijing` 调工具，再把"Beijing：26°C，阴"转回中文自然语言回答。

### 6.4 容错

| 失败 | 处理 |
|---|---|
| 天气 API 不可达 / 超时 | `get_weather` 返回 `"(天气服务暂不可用)"`，LLM 据实告知（不瞎编） |
| 城市找不到 | 返回 `"(找不到城市: X)"` |
| function-calling 端点不支持 | tool_agent 回退常识兜底，`source=fallback_unverified` |

## 七、source 与前端

- 新增 `source="tool"`（🔵 info 蓝色徽章）—— `badge.tsx` 加 `info` variant
- 工具调用过程复用 `thought` SSE 通道：`writer({"tag":"tool_call", "name":"get_weather", "args":{...}, "result":"..."})`
- 前端 `Chat.tsx` 思考过程面板按 `tag` 区分：
  - `tool_call` → 🔧 工具卡（Wrench 图标 + 工具名 + 参数 + 结果）
  - `search` → 🔍 检索卡（原有）

## 八、三场景数据流

| 场景 | 流程 | source |
|---|---|---|
| "北京今天天气" | route(tool_call) → tool_agent[get_weather→26°C→流式答] → END | 🔵 tool |
| KB 无证据的实时问题 | route(kb) → retrieve → grade(无证据) → tool_agent[调工具/常识] → END | 🔵 tool 或 🟡 fallback |
| 正常 KB 问题 | route(kb) → retrieve → grade → generate → verify | 🟢 kb_grounded（不变） |

## 九、验证

`scripts/test_tool_calling.py`（全过）：
- "北京今天天气怎么样" → `source=tool` + 出现 tool_call thought + **无 retrieve**（router 直判跳 KB）
- "你好" → non_kb（回归）
- "什么是 HTTP 协议" → open_qa（回归）

## 十、扩展性

下次加工具（如汇率）：`tools.py` 加一个 `TOOL_SPEC` + 执行函数 + 进 `EXTERNAL_TOOLS` + `_dispatch_tool` 加分支——**router 和前端都不用改**。
