# 整体架构设计

## 一、分层架构

DeepRAG 采用**前后端分离 + 三存储 + Agent 编排**的分层架构：

```
┌─────────────────────────────────────────────────────────┐
│  前端 (web/, React 19 + Vite, :5173)                     │
│  Chat / KnowledgeBase / Monitor / Login                  │
│  ─ SSE 流式(逐字) ─ 思考过程面板 ─ 来源徽章 ─ 拖拽上传     │
└───────────────┬─────────────────────────────────────────┘
                │ REST (axios) + SSE (fetch)
                ▼
┌─────────────────────────────────────────────────────────┐
│  后端 API 层 (apps/api/, FastAPI, :8000)                 │
│  auth / kb / documents / query / conversations / monitor │
│  ─ JWT 鉴权 ─ BackgroundTasks 入库 ─ SSE 事件流           │
└───────┬───────────────────────┬─────────────────────────┘
        │                       │
        ▼                       ▼
┌──────────────────┐   ┌─────────────────────────────────┐
│  Agent 编排层     │   │  入库 Worker (apps/worker/)      │
│  (src/agents/)   │   │  解析→分块→向量化→落库           │
│  LangGraph 状态机 │   └──────────┬──────────────────────┘
│  route→retrieve  │              │
│  →grade→generate │              │
│  →verify (+工具) │              │
└──┬───────────────┘              │
   │ 调用                          │
   ▼                              │
┌──────────────────┐              │
│ 检索层            │              │
│ (src/retrieval/) │              │
│ hybrid / rerank  │              │
└──┬───────────────┘              │
   │                              │
   └──────────┬───────────────────┘
              ▼
   ┌──────────────────────────────────────┐
   │       存储适配层 (src/storage/)        │
   │  MySQL(元数据) │ Qdrant(向量) │ OSS(文件) │
   └──────────────────────────────────────┘
              ▲
              │ 外部依赖
   ┌──────────┴───────────┐
   │ SiliconFlow 网关       │
   │ (Embedding/Rerank/LLM) │
   └──────────────────────┘
```

**设计原则**：
- **分层解耦**：API / Agent / 检索 / 存储各司其职，通过协议（`src/storage/protocol.py`）交互
- **协议优先**：`Retriever` / `ObjectStore` 定义抽象接口，生产实现可替换（如 Qdrant 换其他向量库）
- **ponytail 简化**：标准库 / 已装依赖优先，最短可用 diff，标注有意的简化

## 二、核心数据流

### 2.1 问答流（Query，核心链路）

用户在 Chat 页提问后的完整流转：

```
用户提问
   │
   ▼
[route 意图路由]  ── 规则快通道(闲聊/能力) → reply_direct  → END (non_kb)
   │              ── tool_call            → tool_agent     → END (tool)
   │              ── open_qa              → open_answer    → END (open_qa)
   │              ── out_of_scope         → END (refused)
   │              ── kb_simple/kb_complex ↓
   ▼
[retrieve 检索]   simple: 单次检索+rerank
   │              complex: ReAct 多跳 agent
   ▼
[grade 评估]      无相关证据 → tool_agent 兜底 ─→ END (tool/fallback_unverified)
   │              有相关证据 ↓
   ▼
[generate 生成]   基于证据 + [n] 引用，流式输出
   ▼
[verify 校验]     grounded + 引用有效 → END (kb_grounded)
   │              不达标且 retry<2 → rewrite → 回到 retrieve
   └─→ 自纠循环（MAX_RETRY=2）
```

**关键**：整个流程通过 SSE 实时推送前端（step 节点进度 + thought 推理 + token 逐字），用户能看到"思考过程"。

详见 [03-混合检索与CRAG生成](03-混合检索与CRAG生成.md) + [04-意图分层路由](04-意图分层路由.md)。

### 2.2 入库流（Ingestion）

用户上传 PDF 后的异步处理：

```
前端拖拽 PDF
   │
   ├─ presign → 拿到 OSS 预签名 PUT URL
   ├─ 浏览器直传 OSS (PUT ArrayBuffer)
   └─ confirm → 后端建 doc/version/job 记录 + 挂 BackgroundTasks
                    │
                    ▼
              [ingest_document 异步]
                    │
       ┌────────────┼─────────────┐
       ▼            ▼             ▼
   PyMuPDF解析  父子分块       状态机推进
   (按页blocks) (small-to-big) PARSING→INDEXING→INDEXED
                    │
                    ▼
   SiliconFlow 向量化 (BGE-M3, 1024维)
                    │
       ┌────────────┼─────────────┐
       ▼            ▼             ▼
   Qdrant入库    OSS存chunk     MySQL存chunks元数据
   (dense+sparse) (child+parent)
```

详见 [02-文档入库流水线](02-文档入库流水线.md)。

## 三、三存储协作模型

DeepRAG 用三个存储各司其职，通过 payload / 外键 / key 约定关联：

```
┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
│     MySQL        │  │     Qdrant       │  │      OSS         │
│  (元数据真相源)   │  │  (检索引擎)       │  │  (文件存储)       │
├─────────────────┤  ├─────────────────┤  ├─────────────────┤
│ knowledge_bases │  │ collection:     │  │ raw/{vid}/原PDF  │
│ documents       │  │   "chunks"      │  │ parsed/{vid}/json│
│ document_versions│ │ point.payload:  │  │ chunks/{vid}/*   │
│ chunks          │  │   kb_id/doc_id/ │  │ parent_chunks/*  │
│ indexing_jobs   │  │   version_id/   │  │                  │
│ conversation_   │  │   content/page  │  │                  │
│   messages      │  │ dense(1024)+    │  │                  │
│                 │  │ sparse(BM25)    │  │                  │
└─────────────────┘  └─────────────────┘  └─────────────────┘
        │                    │                    │
        └────── document_versions.id = version_id ──→ 贯穿三存储的关联键
```

**为什么三存储**：
- **MySQL**：强一致的元数据 / 审计 / 事务（软删、级联）
- **Qdrant**：高效的向量 + BM25 混合检索（服务端融合）
- **OSS**：低成本大文件存储（PDF / chunk 文本）

**关键关联**：`version_id` 贯穿三存储——MySQL 的 `document_versions.id`、Qdrant payload 的 `version_id`、OSS 的 key 前缀，三者通过它关联，使得删除时能跨存储精确定位清理。

详见 [07-后端API与存储栈](07-后端API与存储栈.md)。

## 四、Agent 状态机概览

核心问答逻辑用 **LangGraph 1.x** 构建为状态机，采用 `Command(goto=...)` 声明式路由（替代旧的 `add_conditional_edges`）：

```
START → route ┬→ reply_direct → END          (闲聊/能力)
              ├→ tool_agent → END             (工具/兜底)
              ├→ open_answer → END            (常识)
              ├→ END                          (越界 refused)
              └→ retrieve → grade ┬→ generate → verify ┬→ END (kb_grounded)
                                   └→ tool_agent         └→ rewrite → retrieve
                                                            └→ END (fallback_unverified)
```

**状态字段**（`AgentState`）核心：`question / query / intent / documents / generation / source / retry_count / verification`。

**8 个节点**：route / reply_direct / tool_agent / open_answer / retrieve / grade / rewrite / generate / verify。

详见 [03-混合检索与CRAG生成](03-混合检索与CRAG生成.md)（CRAG 部分）+ [04-意图分层路由](04-意图分层路由.md)。

## 五、关键架构决策

| 决策 | 选择 | 理由 |
|---|---|---|
| Agent 编排 | LangGraph 1.x Command 路由 | 声明式、路由逻辑内聚到节点、支持 checkpointer 持久化 |
| 检索融合 | Qdrant 服务端 RRF（dense 主导） | 零客户端再排，服务端高效；BM25 走 `Qdrant/bm25` 原生 |
| 异步入库 | FastAPI BackgroundTasks | Celery + redis RESP3 兼容死结，进程内异步更简单（MVP） |
| 删除策略 | 软删元数据 + 物理清理存储 | 元数据可审计可恢复，Qdrant 必须硬删（否则被检索到） |
| 前端流式 | 原生 fetch + SSE | axios 流式支持差；逐字打字机 + 思考过程提升体验 |
| LLM 接入 | httpx 直连 OpenAI 兼容网关 | 不引入 langchain，轻量可控 |
