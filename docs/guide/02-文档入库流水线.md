# 文档入库流水线

> 从用户上传 PDF 到向量可检索的完整链路。涉及 `apps/api/documents.py`、`apps/worker/ingestion*.py`、`src/storage/*`。

## 一、端到端流程

| 阶段 | 函数 | 位置 | 动作 |
|---|---|---|---|
| 1. 预签名 | `presign_upload` | `documents.py:88-98` | 生成 `version_id`，构造 **ASCII** OSS key，返回 PUT URL |
| 2. 浏览器直传 | — | OSS（前端） | 前端 PUT 文件到 presigned URL |
| 3. 确认入库 | `confirm_upload` | `documents.py:101-127` | 写 documents/versions/jobs 三表，挂 BackgroundTasks |
| 4. 入库编排 | `ingest_document` | `ingestion.py:26-36` | 状态机驱动 PARSING→INDEXING→INDEXED/FAILED |
| 5. PDF 解析 | `parse_document_from_oss` | `ingestion_core.py:90-116` | OSS 取 PDF → PyMuPDF 解析 → 回写 parsed JSON |
| 6. 分块+向量化+落库 | `index_chunks_to_qdrant` | `ingestion_core.py:118-211` | 切分 → embedding → 写 Qdrant+OSS+MySQL |
| 状态更新 | `_update_status` | `ingestion.py:10-23` | 同步更新 versions.status 与 jobs.status |

```
presign → 前端PUT(OSS) → confirm(建表+挂后台) → ingest_document
                                                   │
                                    ┌──────────────┼──────────────┐
                                    ▼              ▼              ▼
                              PyMuPDF解析     父子分块        SiliconFlow向量化
                                    │              │              │
                                    └──────────────┴──────────────┘
                                                   │
                                    ┌──────────────┼──────────────┐
                                    ▼              ▼              ▼
                                Qdrant入库      OSS存chunk      MySQL存元数据
```

## 二、PDF 解析

**`parse_document_from_oss`** (`ingestion_core.py:90-116`)

- **库**：PyMuPDF（`import fitz`）。**Docling 已弃用**——其在 Windows 中文用户名路径下有 C 扩展编码 bug（读不到包资源）。
- **打开方式**：`fitz.open(stream=pdf_data, filetype="pdf")` —— 从 **bytes** 打开，绕过文件系统路径，规避中文路径问题。
- **抽取粒度**：按页 `page.get_text("blocks")`，段落级块，每块带 `{text, page: i+1}`（页码从 1 计）。
- **产物**：序列化为 `{"texts":[...]}`，put 到 `parsed/{version_id}/document.json`。

> 💡 页码随块进入 chunk 的 `locator.page`，最终落到 Qdrant payload 与 MySQL chunks 表——这是生成答案时能标注"第 N 页"引用的基础。

## 三、分块策略：Small-to-Big 父子块

**`split_parent_child`** (`ingestion_core.py:57-88`)

采用 **small-to-big 父子块**设计，而非定长切分：

```
PDF block(段落)         ┌─ child (id=UUID, parent_id=UUID)  ← 检索命中单元 / 可引用
   │                    │
   ├─ block1 ──────────►├─ child
   │                    │   parent_content 累积 child 内容 + "\n\n"
   ├─ block2 ──────────►├─ child
   │                    │
   └─ ...               └─ 父块达 4000 字符 → 切割, 重新生成 parent_id
```

- 每个 PyMuPDF block = 一个 **child**（检索命中的最小单元，可精确引用）
- **parent_content** 顺序累积 child 内容，**父块阈值 4000 字符**，超限切割
- **无显式 chunk_size / overlap**——"重叠"通过父子天然包含关系实现：检索命中 child 后，可回拉 parent 做 **context expansion**（给 LLM 更完整上下文，同时引用指向精确片段）
- point id 必须是纯 UUID（非 `uuid-offset`），否则 Qdrant 拒收

## 四、向量化

### Dense（稠密向量）

**`get_embeddings_siliconflow`** (`ingestion_core.py:19-40`)

- **服务**：SiliconFlow `/embeddings` 接口
- **模型**：`BAAI/bge-m3`（多语言，中英都强）
- **维度**：**1024**（`EMBEDDING_DIMENSIONS`，与 Qdrant collection `size=1024` 对齐）
- **批量**：32 条/批（`BS=32`），按响应内 `index` 回填防乱序
- **query 侧**：`embed_query` (`src/retrieval/embedder.py:15-27`)，单条 + 3 次重试退避

### Sparse（稀疏向量，真 BM25）

> ⚠️ **演进点**：W1 阶段 SiliconFlow 只给 dense、sparse 是 mock；**W2 起已切换为 Qdrant 原生 BM25**。

- `chunk["sparse_text"] = chunk["content"]`（原文，`ingestion_core.py:52`）
- 写入时包成 `Document(text=..., model="Qdrant/bm25")`（`qdrant_store.py:46`）
- 由 **Qdrant 服务端原生 BM25** 计算，`SparseVectorParams(modifier=Modifier.IDF)`（`qdrant_store.py:31`）

**Tokenizer（默认不启用）**：`src/retrieval/tokenizer.py` 提供 jieba 分词，但 W3.1 实验证伪——jieba 分词后 BM25 因"共有词噪声"反而拉低 hybrid 排序（如"法国首都"分词后"首都"与"英国首都"共有，误命中干扰项）。故 sparse 默认走**原文字符级匹配**。

## 五、入库写入（三存储）

### Qdrant（`insert_chunks` @ `qdrant_store.py:41-51`）

collection `chunks`，每个 point：

```
id        = child UUID
vector    = { dense: [1024浮点], sparse: Document(Qdrant/bm25) }
payload   = {
    tenant_id: "default",
    kb_id, document_id, version_id, parent_id,
    page, heading_path: [],
    acl_tags: ["default"],
    content: <child 原文>        ← 关键：零 IO 直取，省 OSS 回拉
}
```

> 💡 **payload 存 content** 是关键优化：检索时直接从 payload 取文本，无需回查 OSS，大幅降低延迟。只有 parent_content（太大）才单独存 OSS 按需拉取。

### MySQL（元数据）

| 表 | 写入时机 | 关键字段 |
|---|---|---|
| `documents` | confirm | id, kb_id, title（软删靠 `deleted_at`） |
| `document_versions` | confirm | id, document_id, oss_key, sha256, status='UPLOADED' |
| `indexing_jobs` | confirm | id, version_id, stage='PARSING', status='PENDING' |
| `chunks` | 入库循环 | id, version_id, parent_id, page, content_hash, oss_key |

### OSS key 命名规则（全 ASCII）

| 用途 | key | 位置 |
|---|---|---|
| 原文 PDF | `raw/{version_id}/{version_id}{ext}` | documents.py:96 |
| 解析产物 | `parsed/{version_id}/document.json` | ingestion_core.py:114 |
| child chunk | `chunks/{version_id}/{chunk_id}.txt` | ingestion_core.py:188 |
| parent chunk | `parent_chunks/{parent_id}.txt` | ingestion_core.py:184 |

## 六、状态机

```
document_versions.status:  UPLOADED → PARSING → INDEXING → INDEXED / FAILED
indexing_jobs.status:      PENDING  → RUNNING  → SUCCESS / FAILED
indexing_jobs.stage:       PARSING → ... (标记当前处理阶段)
```

前端 KnowledgeBase 页通过 `refetchInterval` 动态轮询（存在 PENDING/PARSING/INDEXING 时每 3s 轮询，否则停止），实时展示入库进度。

## 七、关键设计决策与坑

1. **Celery → BackgroundTasks**（`ingestion.py:1-2` 注释）：原 Celery 方案因 `redis-py 8.0` RESP3 与远程 Redis（云代理）HELLO 不兼容放弃，改 FastAPI 进程内 `BackgroundTasks`。代价：阻塞 confirm 响应到入库完成（MVP 可接受）。

2. **Docling → PyMuPDF**：Docling 中文用户名路径编码 bug，弃用；PyMuPDF 从 bytes 打开绕过文件系统。

3. **presigned PUT 的 ASCII key**（`documents.py:92-96`）：中文/全角文件名导致 URL 重编码与签名失配 → 浏览器 403。解法：OSS key 只含 `version_id + 扩展名`。

4. **presign headers 为空 + 前端用 ArrayBuffer**（`oss.py:17-20`）：`presign_upload` 返回 `headers={}`，未强制 Content-Type。前端 PUT 必须用 `await file.arrayBuffer()` 而非 `File`——否则浏览器给 File 自动加 `Content-Type`，而 presigned 签名不含 CT，OSS 验签会 `SignatureDoesNotMatch 403`。

5. **Qdrant host 须带 http scheme**（`_normalize_host` @ `qdrant_store.py:14-18`）：服务端是 http，host 无 scheme 时 qdrant_client 默认 https → `SSL:WRONG_VERSION_NUMBER`。

6. **document_id payload bug 修复**（`ingestion_core.py:156`）：历史 payload 把 `document_id` 误写成 `version_id`，导致按文档删/过滤错乱；已修——confirm 传真 `document_id` 入库，旧调用兜底 `version_id`。

7. **payload 存 content**（零 IO）：检索时直接从 Qdrant payload 取文本，避免每次检索回查 OSS + MySQL。
