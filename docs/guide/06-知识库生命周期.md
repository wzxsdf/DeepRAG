# 知识库生命周期管理

> 企业级数据治理：创建 / 删除 / 改名，跨三存储一致性。涉及 `apps/api/kb.py`、`documents.py`、`src/storage/*`。
> 设计文档：`docs/superpowers/specs/2026-08-02-kb-lifecycle-design.md`

## 一、背景

W1-W3 只有"建 KB + 上传文档"，**无删除 / 更新**。企业场景下，知识库会过期、会废弃、会重命名——必须有完整的生命周期管理，且**不能留垃圾**（删了 KB 但向量还在 → 被检索到 = 错误答案）。

## 二、删除策略：软删元数据 + 物理清理

| 层 | 做法 | 理由 |
|---|---|---|
| **MySQL 元数据** | 软删（`deleted_at` + `deleted_by` + `status`） | 可审计、可追溯、列表过滤即可"消失" |
| **Qdrant 向量** | **物理硬删** | ⚠️ 关键：软删的 chunks 若不摘除，**仍会被检索到 = 错误答案**。不能用 payload 软标记 + 查询过滤（每次检索背 filter 成本） |
| **OSS 文件** | 物理删（释放空间） | 文件无检索价值，直接清 |

> 💡 **RAG 删除的铁律**：Qdrant 必须立即硬删。这是 RAG 系统区别于普通 CRUD 的关键——检索引擎不认"软删"。

## 三、跨存储一致性（企业思维）

三个存储，如何保证删干净又不一致性？三个原则：

### 3.1 清理顺序：先 Qdrant → OSS → MySQL 事务

```
① Qdrant 先删   ← 隔离检索(立即不再命中, 防删除期间被查到)
② OSS 删        ← 释放空间
③ MySQL 事务    ← 子表物理删 + 主表软删(原子提交)
```

**为什么 Qdrant 先**：检索是面向用户的实时路径，必须最先隔离；MySQL 事务最后提交，确保元数据与物理状态最终一致。

### 3.2 MySQL 级联用事务

`execute_transaction`（`mysql.py` 纯执行层）：单连接内 `begin / commit / rollback`，保证"删 chunks + jobs + versions + 软删 documents"原子性。（默认 autocommit=True 无事务，故需显式事务。）

> 阶段 4 后，级联 SQL 下沉到 `DocumentRepository.purge_with_versions`（事务内调 `execute_transaction`），`purge_document` 编排函数调它 + Qdrant/OSS。

### 3.3 Qdrant/OSS 幂等可重试

删已删不报错：
- OSS：`NoSuchKey` 静默（`oss.py:34-39`）
- Qdrant：`delete` 空集不报错

→ 失败可重试，无副作用。

## 四、单文档清理：purge_document

**`purge_document`** (`documents.py`)——单文档物理清理的**唯一实现**，被 `DELETE /documents/{id}` 和 `DELETE /kbs/{id}` 复用（DRY）。阶段 4 后 MySQL 侧经 `DocumentRepository.purge_with_versions`（事务级联），Qdrant/OSS 仍在编排函数内删。

**清理清单**（删单文档）：

```
① Qdrant: delete_by_version(version_id)          隔离检索
② OSS:    原 oss_key + parsed/{vid}/ + chunks/{vid}/ + parent_chunks/{pid}.txt
③ MySQL:  事务 DELETE chunks/jobs/versions + UPDATE documents 软删
```

## 五、删知识库：delete_kb

**`delete_kb`** (`kb.py:82-110`)——单连接内完成，循环复用 `purge_document`：

```
1. 禁删 default KB
2. 幂等检查(裸查询, 不过滤 deleted_at)  ← 见坑①
3. set_kb_status(DELETING)               ← 并发保护
4. 循环 purge_document(每篇文档)         ← 复用 DRY
5. Qdrant delete_by_kb 兜底清一次         ← 防逐 version 遗漏
6. soft_delete_kb (deleted_at + status=DELETED)
```

> 💡 **第 5 步兜底**：因历史 `document_id=version_id` 脏 payload，逐 version 删可能遗漏；按 `kb_id` 兜底清一次确保干净。

## 六、状态机：并发保护

```
ACTIVE  ──(删除请求)──→  DELETING  ──(清理完成)──→  DELETED
 可读写                    中间态                     终态(列表过滤)
                          上传被拒(409)
```

**并发互斥**：`confirm_upload` 上传时校验 KB `status`，**DELETING / DELETED 拒绝上传（409）**——防止"删 KB 期间有人上传新文档"的不一致。

## 七、改名

`rename_kb` (`kb.py:67-79`)：`UPDATE knowledge_bases SET name`。纯元数据，不动物理层。前端弹窗禁用"空名 / 与原名相同"。

## 八、关键坑（非显而易见）

### 坑①：幂等检查不能用 get_kb

`get_kb` 过滤了 `deleted_at IS NULL`，已软删的 KB 查不到 → 返回 404。导致**重复删除返回 404 而非幂等 200**。

**修**：`delete_kb` 用**不过滤**的裸查询 `SELECT id, deleted_at FROM knowledge_bases WHERE id=%s`，已删直接返回幂等成功。

> 💡 这是软删除 + 过滤查询设计的**典型陷阱**：用于"列表展示"的过滤查询，不能复用于"幂等检查"。

### 坑②：删 KB 须单连接内完成

`purge_document` 复用已 connect 的 mysql 连接，**不能中途 close**（pool 失效）。整个 `delete_kb` 在单连接内完成。

### 坑③：后端改代码须重启

uvicorn 无 reload，改代码后须重启；旧进程占 8000 → 新进程 bind 失败。重启前 `netstat -ano | grep :8000 | grep LISTENING` 抓 PID，`taskkill //F //T //PID`。

## 九、验证

`scripts/test_kb_lifecycle.py`（全过）：
- 传 2 文档 → 删 1（向量 4→2，doc_count=1，列表过滤）
- 删 KB（向量 0，documents_removed=1）
- 幂等再删 → 200
- 检索该 KB → citations=0（隔离生效）
